# Local Thermal Printer Support — Delivery Report

This document is the delivery record for the local thermal printer feature: a
standalone **Print Agent** that runs on a restaurant's own computer and lets
the Mero Restro web app print receipts and kitchen tickets directly to a
USB or LAN-connected ESC/POS thermal printer (e.g. a ZKTeco ZKP8018, 80mm),
without breaking or replacing the existing browser `window.print()` receipt
flow. It covers what changed, how to set it up, and how to verify it.

## 0. Post-delivery fix: Chrome Private Network Access (PNA)

**Symptom:** `GET http://127.0.0.1:<port>/health` never returns a usable
response from the browser — it shows in the Network tab but effectively
fails, so Settings → Printers never reaches "Connected" and "Detect
printers" has nothing to work with (the agent is never reachable in the
first place, so this is a single root cause, not two separate bugs).

**Cause:** Chrome's Private Network Access spec treats any page NOT itself
served from a loopback address (the deployed `https://app.merorestroapp.com`,
or a dev server reached via a LAN IP) as "public"/"private" address space.
Fetching a "local" address like `127.0.0.1` from there forces a preflight
`OPTIONS` request carrying `Access-Control-Request-Private-Network: true` —
even for a plain unauthenticated `GET /health` that wouldn't otherwise need
a preflight — and Chrome silently fails the real request unless the server
echoes back `Access-Control-Allow-Private-Network: true` on that preflight.

**Fix:** `src/security.ts`'s `originGuard` now sets that header whenever the
preflight requests it. If you're running the agent via `npm run dev`
(ts-node-dev), it auto-restarts on save and picks this up immediately —
just retry. If you're running a packaged binary, rebuild
(`npm run build && npm run package:win` / `:mac`) and relaunch it.

If connectivity still fails after that: confirm the exact page origin
you're testing from is in `ALLOWED_ORIGINS` (`src/config.ts`) — a LAN IP
like `http://192.168.x.x:5173` is NOT in that list by default and gets a
403 (visible in the response body, not a silent failure) rather than this
issue.

## 0.1 Desktop installer packaging (Electron tray app)

The agent used to only run as `npm run dev` / a `pkg`-built binary launched
by hand, with auto-start wired via a shell script the customer had to run
in Terminal (`scripts/install-macos-launchagent.sh`) or PowerShell
(`scripts/install-windows-startup.ps1`). That's no longer what customers
use — see the main implementation report for the full rationale and
acceptance criteria. In short:

- `electron/main.js` is a plain-CommonJS Electron **tray-only** wrapper
  (no window, no Dock icon) that calls `startAgentServer()` — the exact
  same Express/CUPS/ESC-POS code, now exported from `src/index.ts` instead
  of only running as a side effect of executing that file directly.
- `npm run build:mac` / `npm run build:win` produce a `.dmg` / `.exe`
  installer under `release/` via `electron-builder`.
- Auto-start at login is now `app.setLoginItemSettings()` (native
  Electron/OS mechanism), not the old shell scripts — those scripts still
  exist for anyone who deliberately wants the raw `pkg` binary instead, but
  are no longer part of the customer-facing install path.
- `npm run dev` / `npm run print-agent` (headless, no Electron) still work
  completely unchanged for local development.
- `build/icon.png` is a **placeholder** generated by
  `scripts/gen-placeholder-icon.js` — replace it with real branding before
  shipping an installer to actual customers.

## 1. Architecture

```
React POS / Settings (app.merorestroapp.com)
        │  fetch → http://127.0.0.1:<38111-38115>
        ▼
Mero Restro Print Agent  (new standalone project, runs on the restaurant's PC)
        │  raw ESC/POS bytes
        ▼
USB spooler  or  TCP :9100 (LAN)
        ▼
Thermal printer (ZKP8018 or any ESC/POS 80mm/58mm printer)
```

The Laravel backend is involved in exactly one way: it stores *which*
printer handles *which role* per organization/branch (a small `printer_configs`
table). It never talks to a printer. All ESC/POS generation and raw
printing happens in the Print Agent, which only accepts connections from
`127.0.0.1` and only from the app's own origin.

## 4. Database migrations

Only one migration belongs to this feature:

`2026_08_27_000003_create_printer_configs_table.php` creates `printer_configs`:

| Column | Notes |
|---|---|
| `organization_id` | FK, cascade delete — tenant-scoped |
| `branch_id` | nullable FK — null = organization-wide default |
| `role` | enum `receipt` / `kitchen` / `bar` |
| `name` | human label shown in Settings |
| `printer_type` | enum `thermal` / `other`, default `thermal` |
| `connection_type` | enum `usb` / `network` |
| `target` | nullable string — OS printer name (USB) or `host:port` (network) |
| `paper_width` | enum `80mm` / `58mm` |
| `copies` | tinyint, 1–5 |
| `auto_print` | bool — fire automatically on checkout |
| `is_active` | bool |

Unique index on `(organization_id, branch_id, role)`. Run with the usual
`php artisan migrate` on the backend — no seed data, no destructive change
to any existing table.

## 5. Environment variables

**None required.** This feature adds no new backend `.env` keys and the
Print Agent has no `.env` file at all — its only persisted state is
`config.json` (port + pairing token), written automatically on first run to
a per-OS local directory (see §9). The frontend needs no new
`VITE_*` variables either; the agent is discovered by probing
`http://127.0.0.1:<port>` directly from the browser, entirely separate from
`VITE_API_BASE_URL`.

## 6. Print Agent setup (general)

1. On the restaurant's computer, build (or receive a pre-built) executable — see §7/§8.
2. Run it once. It prints its pairing token to its own console/window and creates `config.json`.
3. In the web app, go to **Settings → Printers**. The "Local Print Agent" card auto-detects the running agent (`Connected` badge).
4. Paste the pairing token shown in the agent's window into the "Pairing token" field and click **Save & pair**. This is a one-time step per computer/browser.
5. Click **Add printer**, pick USB or Network, click **Detect printers** (USB) or type the printer's `host:port` (network), then **Test print** to confirm before saving.

The agent never needs Node, Python, or PHP installed on the restaurant's
machine when built as a standalone executable (`pkg`) — see §7/§8.

## 7. Windows install

```powershell
# On a Windows machine, from the mero-restro-print-agent folder:
npm install
npm run build
npm run package:win        # -> dist-pkg\mero-restro-print-agent-win.exe
```

Copy `dist-pkg\mero-restro-print-agent-win.exe` to the restaurant's PC and
run it. To start it automatically every login:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\install-windows-startup.ps1
```

This creates a shortcut in the current user's Startup folder pointing at
the executable — no admin rights, no service installation.

**USB printing on Windows** goes through the `printer` npm package (native
addon wrapping the Win32 spooler's raw `WritePrinter` call). It's an
optional dependency — `npm install` must run on Windows (or with
`--target_platform=win32` cross-compile tooling) so `pkg` bundles a working
prebuilt binary. If it's ever missing, the agent still runs; USB printing
returns a clear "USB printing isn't available on this build — use network
printing instead" error, and network (LAN, `host:port`) printing is
completely unaffected since it's a plain TCP socket.

## 8. macOS install

```bash
# On a Mac, from the mero-restro-print-agent folder:
npm install
npm run build
npm run package:mac        # -> dist-pkg/mero-restro-print-agent-macos (x64 + arm64)
```

Run it once manually to confirm it starts, then install as a LaunchAgent so
it starts at every login:

```bash
chmod +x scripts/install-macos-launchagent.sh
./scripts/install-macos-launchagent.sh
```

This copies `scripts/com.merorestro.printagent.plist` into
`~/Library/LaunchAgents`, fills in the real executable path, and runs
`launchctl load`. To stop/start it later: `launchctl unload` /
`launchctl load` the same plist path (the installer script prints the exact
path). USB printing on macOS goes through CUPS (`lp -o raw`) — no native
addon needed, works out of the box.

## 9. ZKP8018 configuration

The agent never assumes a printer is literally named "ZKP8018" — it always
asks the OS for the real name via **Detect printers** in Settings.

**USB:** install the ZKP8018's normal driver on the restaurant's computer
first (as any USB printer). Once it shows up in the OS's printer list, open
Settings → Printers → Add printer → Connection type "USB" → **Detect
printers** → pick it from the list → **Test print**.

**Network (Wi-Fi/Ethernet):** put the printer on the restaurant's LAN via
its own network setup menu, note the IP address it's assigned, and enter
`<that-ip>:9100` as the target (`9100` is the printer's raw/JetDirect port —
standard for ESC/POS network printers including the ZKP8018). No driver
install needed for network printing; it's a plain TCP socket write.

Either way, always confirm with **Test print** (Settings) or the "Print
thermal receipt" button (checkout/Billing History) before relying on it —
the test slip is fully self-contained and doesn't require an internet
connection, matching the "works offline, on the restaurant's own LAN"
requirement.

## 11. Production deployment considerations

- **The Print Agent is never deployed to a server.** It's an executable
  the restaurant runs on their own computer, once, alongside their POS
  browser tab — it is not part of the Laravel/Vite deployment pipeline for
  `api.merorestroapp.com` / `app.merorestroapp.com`.
- **Origin allowlist:** `src/config.ts`'s `ALLOWED_ORIGINS` hard-codes
  `https://app.merorestroapp.com` as the only production origin. If the
  app's production domain ever changes, that list (and the matching
  `printer-agent.ts` `CANDIDATE_PORTS`/discovery logic on the frontend,
  which doesn't need updating) is the one place to edit and re-package.
- **HTTPS page → HTTP localhost:** `app.merorestroapp.com` is served over
  HTTPS, and the agent listens on plain HTTP `127.0.0.1`. Browsers treat
  `http://127.0.0.1`/`http://localhost` as a "potentially trustworthy"
  origin exception specifically to allow this pattern (mixed-content
  blocking does not apply to loopback addresses) — no browser flags or
  user overrides are required, and nothing here weakens the page's own
  HTTPS.
- **No inbound firewall changes needed** on the restaurant's router/network
  for USB printing (loopback only) or typical network printing (agent
  makes an outbound LAN connection to the printer's `:9100`, nothing needs
  to accept inbound traffic).
- **Backend:** run the one migration (`printer_configs`) as part of the
  normal deploy migrate step; no other backend changes ship to production.
- **Distribution:** the built `.exe` (Windows) and macOS binaries are not
  currently hosted anywhere public — for now, hand them to restaurants
  directly (e.g. a private download link or USB drive) until/if a proper
  release/update channel is set up. That's a deliberate scope boundary for
  this pass, not an oversight.

## 12. Testing checklist

Automated coverage was not added for this feature (no PHPUnit test
scaffolding was extended, and the agent has no test runner configured) —
this checklist is a manual verification pass; run it once per environment
(dev, then production) before considering it live.

Backend
- [ ] `php artisan migrate` runs `create_printer_configs_table` cleanly on a fresh and on an existing database.
- [ ] `GET/POST/PUT/DELETE /api/v1/printer-configs` all reject cross-tenant access (org A cannot see/edit org B's printers).
- [ ] Creating a second printer for the same `(branch, role)` is rejected with a clear validation error (app-level duplicate guard in the controller, not just the DB unique index).

Print Agent
- [ ] `npm run dev` starts and prints a port + pairing token to the console.
- [ ] `GET http://127.0.0.1:<port>/health` returns `{ success: true }` with no token.
- [ ] `GET /printers` lists at least one real OS-installed printer.
- [ ] `POST /print` and `/test-print` reject requests missing `X-Print-Agent-Token` or sent with the wrong token.
- [ ] `POST /print` from a browser tab on a non-allowlisted origin (e.g. `http://evil.example`) is rejected server-side, not just hidden by CORS.
- [ ] Sending the same `idempotencyKey` twice within 2 minutes returns the original job instead of printing twice; the same key after 2+ minutes prints again.

Frontend — Settings → Printers
- [ ] Agent status badge shows Connected/Disconnected/Checking correctly as the agent is started/stopped.
- [ ] Pairing token save/re-pair works; an obviously wrong token produces an actionable Test Print failure message, not a generic error.
- [ ] Detect printers lists the OS's real printers for USB connection type.
- [ ] Test print produces a physical slip on both a USB and a network-connected printer.
- [ ] Add/Edit/Delete printer all work and are reflected immediately in the list.

Frontend — checkout / billing
- [ ] TablesReservations → close a bill with an auto-print receipt printer configured: thermal receipt prints automatically, checkout still succeeds even if the printer is off (toast shows the printer error, order is not rolled back or blocked).
- [ ] "Print thermal receipt" button (open bill preview, closed receipt view, and Billing History reprint) all print correctly and never touch `window.print()`'s existing behavior — the "Print bill" / "Print" browser-print buttons are untouched and still work exactly as before.
- [ ] With the agent not running, every thermal print action shows "⚠ Print Agent Not Running" with clear next steps and does not throw or freeze the page.
- [ ] Kitchen ticket content (via `printKitchenOrder`, exposed on `usePrinter` for future wiring) never includes payment information — verified in `escpos/kitchenTicketBuilder.ts`.

## Known limitation from this delivery pass

The `mero-restro-print-agent` project could not be `npm install`'d or
type-checked in the environment this was built in (no outbound access to
the npm registry there). Every file was manually reviewed line-by-line for
TypeScript correctness instead. **Run `npm install && npm run build` in
this project yourself as the first real verification step** — that's the
one thing in this delivery that hasn't been machine-verified.
Everything in `rms-backend` (PHP brace-balance across every touched file)
and `rms-frontend` (`npx tsc -b` and `npx eslint src` across the entire
project, not just touched files) has been verified clean.
